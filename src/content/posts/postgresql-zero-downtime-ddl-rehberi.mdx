Canlı bir PostgreSQL veritabanında `ALTER TABLE` veya `CREATE INDEX` gibi DDL komutları çalıştırmak, yanlış yönetildiğinde saniyeler içinde tüm API sunucularının bağlantı havuzlarını doldurabilir ve tam bir servis kesintisine (downtime) yol açabilir.

---

## 1. En Büyük Tehlike: Lock Queue Starvation

Bir `ALTER TABLE` komutu sadece 1 milisaniyelik bir işlem yapsa dahi `AccessExclusiveLock` talep eder. Eğer o anda tabloda 30 saniye süren uzun bir `SELECT` varsa, DDL işlemi bu sorgunun bitmesini beklemek üzere kilit kuyruğuna girer.

**Tehlike şudur:** PostgreSQL, kilit açlığını önlemek için kuyrukta bekleyen `AccessExclusiveLock` talebinden sonra gelen **tüm yeni `SELECT` sorgularını da bloke eder!**

## 2. Kesintisiz DDL İçin Dört Altın Kural

### Kural 1: Daima `CREATE INDEX CONCURRENTLY` Kullanın
Standart `CREATE INDEX`, tabloya yazma (`INSERT/UPDATE/DELETE`) yapılmasını engeller. `CONCURRENTLY` anahtar kelimesi ise iki aşamalı çalışarak DML trafiğini engellemez:
- Bir transaksiyon bloğu (`BEGIN ... COMMIT`) içinde çalıştırılamaz.
- Başarısız olursa indeksi `INVALID` bırakır (`DROP INDEX CONCURRENTLY` ile temizlenmelidir).

### Kural 2: İki Adımlı Constraint: `NOT VALID` + `VALIDATE`
Milyonlarca satırlık bir tabloya doğrudan `ADD CONSTRAINT ... FOREIGN KEY` eklemek tüm tabloyu tararken `AccessExclusiveLock` tutar. Bunun yerine:

```sql
-- 1. Adım: Sadece yeni yazılan satırları denetler (Kilit süresi: < 1ms)
ALTER TABLE orders ADD CONSTRAINT fk_user
FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;

-- 2. Adım: Eski satırları doğrular (ShareUpdateExclusiveLock: SELECT ve INSERT engellenmez!)
ALTER TABLE orders VALIDATE CONSTRAINT fk_user;
```

### Kural 3: PostgreSQL 11+ İle `DEFAULT` Kolon Ekleme
PostgreSQL 11 ve sonrasında sabit bir varsayılan değerle sütun eklemek (`ALTER TABLE t ADD col text DEFAULT 'active'`) fiziksel satırları yeniden yazmaz; katalog metadata'sını günceller. Saniyeler değil milisaniyeler sürer.

## 3. Production Migration Şablonu: Kısa `lock_timeout` ve Retry

Bir migrasyon scripti asla sınırsız kilit beklememelidir. Kısa bir `lock_timeout` atanmalı, kilit anında alınamazsa kuyruk temizlenmeli ve işlem tekrar denenmelidir:

```sql
-- Güvenli Migrasyon Wrapper Deseni
DO $$
DECLARE
    attempts int := 0;
BEGIN
    LOOP
        BEGIN
            -- Kilidi en fazla 2 saniye bekle, alamıyorsan vazgeç:
            SET LOCAL lock_timeout = '2s';
            
            ALTER TABLE orders ADD COLUMN priority int DEFAULT 1;
            EXIT; -- Başarılı ise döngüden çık
        EXCEPTION
            WHEN lock_not_available THEN
                attempts := attempts + 1;
                IF attempts > 5 THEN
                    RAISE EXCEPTION 'Migrasyon kilit alamadı, işlem iptal edildi.';
                END IF;
                PERFORM pg_sleep(2); -- 2 saniye bekle ve tekrar dene
        END;
    END LOOP;
END $$;
```

## 4. Laboratuvar: `NOT VALID` Constraint Deneyimi

### Adım 1: Büyük Tablo ve Kısıt Eklenmesi
```sql
CREATE TABLE users (id int PRIMARY KEY);
INSERT INTO users VALUES (1), (2);

CREATE TABLE orders (id int PRIMARY KEY, user_id int);
INSERT INTO orders SELECT g, 1 FROM generate_series(1, 100000) g;
```

### Adım 2: Hızlı Kilit ve Arka Planda Doğrulama
```sql
-- Kilitlenmeyi sıfıra indiren adım:
ALTER TABLE orders 
ADD CONSTRAINT fk_orders_user 
FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;

-- Tablo aktif trafik alırken arka planda güvenle doğrulanır:
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_user;
```

### Adım 3: `CONCURRENTLY` Sırasında `INVALID` İndeks Tespiti ve Temizliği
`CREATE UNIQUE INDEX CONCURRENTLY` işlemi ikinci fazda tekrar eden (duplicate) veri nedeniyle başarısız olursa indeks silinmez; katalogda `INVALID` olarak kalır:

```sql
CREATE TABLE conc_test (id int, email text);
INSERT INTO conc_test VALUES (1, 'a@test.com'), (2, 'a@test.com');

CREATE UNIQUE INDEX CONCURRENTLY idx_conc_email ON conc_test (email);
```

Alınan gerçek hata ve katalog durumu:
```text
ERROR:  could not create unique index "idx_conc_email"
DETAIL:  Key (email)=(a@test.com) is duplicated.
```

```sql
SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index
WHERE indexrelid = 'idx_conc_email'::regclass;
```

```text
   indexrelid   | indisvalid | indisready 
----------------+------------+------------
 idx_conc_email | f          | f
(1 row)
```

`INVALID` indeksler okuma sorgularında kullanılmaz ancak her `INSERT/UPDATE` işleminde güncellenerek gereksiz yazma maliyeti üretir. Trafiği kesmeden `DROP INDEX CONCURRENTLY idx_conc_email;` komutuyla temizlenmelidir.

Bu yöntemle canlı veritabanlarında milyarlarca satırlık tablolara dahi tek bir kullanıcı isteğini düşürmeden veri bütünlüğü kuralları eklenebilir.
