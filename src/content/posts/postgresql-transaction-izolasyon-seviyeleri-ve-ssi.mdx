SQL standardı 4 transaction izolasyon seviyesi tanımlar. Ancak PostgreSQL'in MVCC çekirdeğinde **`Read Uncommitted` bulunmaz**; kirli okuma (**Dirty Read**) mimari gereği imkansız olduğu için bu seviyede talep edilen transaksiyonlar doğrudan `Read Committed` olarak çalıştırılır.

---

## 1. PostgreSQL İzolasyon Matrisi ve Anomaliler

PostgreSQL çekirdeğinde 3 gerçek izolasyon seviyesi bulunur:

| İzolasyon Seviyesi | Snapshot Alınma Zamanı | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly (Write Skew) |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **`Read Committed`** (Varsayılan) | **Her SQL ifadesinin başında** yeni snapshot | İmkansız | Mümkün | Mümkün | Mümkün |
| **`Repeatable Read`** | **Transaksiyonun ilk sorgusunda** tek snapshot | İmkansız | İmkansız | İmkansız | Mümkün |
| **`Serializable` (SSI)** | İlk sorguda snapshot + SIREAD kilit takibi | İmkansız | İmkansız | İmkansız | **Engellenir** |

---

## 2. SSI (Serializable Snapshot Isolation) Nasıl Çalışır?

Klasik veritabanları tam seri hale getirilebilirliği (Serializability) sağlamak için tüm okunan satırları kilitleyen ağır **Two-Phase Locking (2PL)** mekanizmasını kullanır. Bu da okuyucuların yazıcıları engellemesine ve performansın çökmesine yol açar.

PostgreSQL ise **SSI** ile okuma kilitleri koymaz:
1. Okunan satırlara ve sayfalara bellek içi **SIREAD Locks** bayrağı koyar (bu bir bekleme kilidi değildir, sadece işaretçidir).
2. Çekirdek, bu işaretçileri kullanarak oturumlar arasındaki bağımlılık grafiğini (**Dependency Graph**) izler.
3. İki transaksiyon arasında bir döngüsel bağımlılık (**rw-antidependency cycle / Write Skew**) oluşursa, PostgreSQL transaksiyonlardan birini iptal eder:
   `ERROR: could not serialize access due to read/write dependencies among transactions`

## 3. Laboratuvar: Repeatable Read ve Serializable Çatışması

### Adım 1: Test Tablosunu Hazırlama
```sql
CREATE TABLE doctor_on_call (
    id int PRIMARY KEY,
    doctor_name text,
    on_call boolean
);
INSERT INTO doctor_on_call VALUES (1, 'Dr. Ali', true), (2, 'Dr. Ayşe', true);
```
*Kural:* Hastanede en az bir doktor nöbette kalmalıdır (`on_call = true`).

### Adım 2: Serializable Write Skew Çatışması
İki terminalde aynı anda `SERIALIZABLE` transaksiyon başlatıp iki doktorun da nöbetten çıkmak istediğini simüle edelim:

```sql
-- Terminal 1:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- Nöbette kaç kişi var kontrol edelim:
SELECT count(*) FROM doctor_on_call WHERE on_call = true; -- (Sonuç: 2)

-- Terminal 2:
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM doctor_on_call WHERE on_call = true; -- (Sonuç: 2)

-- Terminal 1 (Ali nöbetten çıkar):
UPDATE doctor_on_call SET on_call = false WHERE id = 1;

-- Terminal 2 (Ayşe de nöbetten çıkar):
UPDATE doctor_on_call SET on_call = false WHERE id = 2;

-- Terminal 1:
COMMIT; -- (Başarılı!)

-- Terminal 2:
COMMIT; -- (HATA ALIR!)
```

Terminal 2 `COMMIT` ettiği anda PostgreSQL döngüsel bağımlılığı yakalar ve verinin bozulmasını engeller:
```text
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during commit attempt.
HINT:  The transaction might succeed if retried.
```

Bu mekanizma sayesinde veritabanında aynı anda iki doktorun da nöbetten çıkması ve nöbetçi doktor sayısının sıfıra düşmesi (Write Skew) önlenmiş olur. Uygulama bu hatayı aldığında transaksiyonu baştan denemelidir (`retry`).
