İki veya daha fazla transaksiyonun birbirlerinin tuttuğu kilitleri karşılıklı olarak talep ettiği ve hiçbirinin ilerleyemediği döngüsel kilitlenme durumuna **Deadlock** denir.

PostgreSQL, deadlock durumunu çözmek için otomatik bir tespit algoritması koşturur ve döngüyü kırmak için transaksiyonlardan birini kurban (**victim transaction**) seçerek hata ile sonlandırır (`ERROR: deadlock detected`).

---

## 1. Deadlock Algılama Mekanizması (`deadlock_timeout`)

Her kilit talebinde deadlock kontrolü çalıştırmak yüksek CPU yükü yaratır. Bu nedenle PostgreSQL iki aşamalı bir strateji izler:

1. Bir süreç kilit alamadığında önce uyku moduna geçer ve Lock Wait kuyruğunda bekler.
2. Bekleme süresi **`deadlock_timeout`** (varsayılan: `1s`) değerini aştığında, çekirdek bir döngüsel bağımlılık (Wait-For Graph) olup olmadığını kontrol eder.
3. Döngü tespit edilirse, sistem maliyeti en düşük olan transaksiyonu `ROLLBACK` ettirir ve diğerinin devam etmesini sağlar.

## 2. Savunma Katmanı: Üç Hayati Timeout Parametresi

Deadlock ve kilitlenme risklerine karşı production veritabanında üç parametrenin mutlaka yapılandırılması gerekir:

| Parametre | Önerilen Değer | Görevi ve Önemi |
| :--- | :--- | :--- |
| **`lock_timeout`** | `2s` - `5s` | Bir kilit edinmek için beklenebilecek maksimum süre. Aşılırsa sorgu anında düşürülür (Lock bekleme kuyruğunda yığılmayı önler). |
| **`statement_timeout`** | `30s` - `60s` | Sorgunun toplam çalışma süresi sınırı. Sonsuz döngüye giren veya çok uzun süren sorguları öldürür. |
| **`idle_in_transaction_session_timeout`** | `10s` - `30s` | `BEGIN` dedikten sonra açık bırakılan atıl oturumları otomatik sonlandırır. Deadlock ve bloat'un 1 numaralı düşmanıdır. |

## 3. Laboratuvar: Deadlock Simülasyonu ve `lock_timeout`

### Adım 1: Deadlock Döngüsü Tetikleme
İki ayrı terminalde aşağıdaki komutları sıra numaralarına göre çalıştırın:

```sql
-- Terminal 1 (Adım 1):
BEGIN;
UPDATE accounts SET balance = balance + 10 WHERE id = 1;

-- Terminal 2 (Adım 2):
BEGIN;
UPDATE accounts SET balance = balance + 20 WHERE id = 2;

-- Terminal 1 (Adım 3):
UPDATE accounts SET balance = balance + 10 WHERE id = 2;
-- (Terminal 1 beklemeye geçer...)

-- Terminal 2 (Adım 4):
UPDATE accounts SET balance = balance + 20 WHERE id = 1;
-- (Deadlock tetiklendi!)
```

Yaklaşık 1 saniye sonra Terminal 2'de aşağıdaki hata görünür:
```text
ERROR:  deadlock detected
DETAIL:  Process 41250 waits for ShareLock on transaction 892; blocked by process 41240.
Process 41240 waits for ShareLock on transaction 893; blocked by process 41250.
HINT:  See server log for query details.
```

### Adım 2: `lock_timeout` ile Fail-Fast Koruması
Deadlock tespitinin 1 saniye beklemesini istemiyorsanız veya yoğun trafikte sorgunun kuyruğu tıkamadan hemen vazgeçmesini istiyorsanız oturum bazında `lock_timeout` tanımlayabilirsiniz:

```sql
-- Terminal 2'de:
SET lock_timeout = '200ms';
BEGIN;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
```

Eğer Terminal 1 satırı tutuyorsa Terminal 2 tam 200 ms sonra beklemeden çıkar:
```text
ERROR:  canceling statement due to lock timeout
```

Bu pratik, mikroservis ve API mimarilerinde connection pool tükenmesini engelleyen en kritik resilience desenidir.
