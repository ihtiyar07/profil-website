## 1. Context
Sapmapayı is an enterprise compliance platform auditing cold-chain integrity across pharmaceutical and perishables storage facilities. It analyzes high-frequency temperature and humidity curves, flags threshold violations, and compiles officially enforceable e-signed audit PDFs.

## 2. Problem
The system encountered two architectural bottlenecks:
1. **Browser Thread Lock on Large Time-Series:** Inspecting a 30-day thermal history for a cold room yielded ~250,000 datapoints. Serializing this into conventional JSON produced a 25MB payload that froze browser JavaScript `JSON.parse()` threads for 800ms+.
2. **Legal Enforceability:** Proving that audit data had not been retroactively altered required cryptographic digital signatures (X.509) and certified RFC 3161 timestamps on all exported reports.

## 3. Architecture & Data Path

Telemetry streaming and notarized compliance reporting operate through four unified layers:

1. **Time-Series Persistence (TimescaleDB):** High-frequency temperature and humidity readings reside in hypertable partitions. 1-minute raw sensor logs are continuously aggregated into hourly rollups on disk.
2. **Binary IPC Streamer (.NET 10 & Apache Arrow):** Query handlers bypass traditional object serialization and JSON loops. Records are transformed directly into Apache Arrow RecordBatch columnar buffers and streamed via PipeWriter over HTTP/WebSocket.
3. **Frontend Zero-Copy Buffer (Canvas & Float64Array):** Incoming Arrow IPC chunks bind directly into JavaScript `Float64Array` typed memory without JSON parsing overhead, driving 60 FPS graphics without thread stutter.
4. **Compliance Document Notarization (PKCS#11 HSM & QuestPDF):** Reports render via native vector PDF layouts (`QuestPDF`) rather than heavy headless browsers. Documents are asynchronously signed using certified X.509 keys and RFC 3161 timestamps via a dedicated PKCS#11 queue.

## 4. Decisions & Rejected Alternatives

- **Apache Arrow IPC chosen, JSON REST API rejected:** String parsing overhead and duplicated JSON dictionary keys caused unacceptable latency. Arrow's columnar memory layout enabled direct mapping from raw database bytes straight into browser `Float64Array` typed memory without intermediate serialization.
- **Asynchronous HSM worker pool chosen, synchronous calls rejected:** Hardware Security Modules (HSMs) operate synchronously with 300–700ms signing latency. Dedicated background worker queues decoupled report generation from interactive web threads.
- **TimescaleDB Continuous Aggregates chosen, document stores rejected:** Pre-computing hourly rollups inside partitioned PostgreSQL hypertables avoided repeated, resource-heavy disk scans on raw telemetry.

## 5. Core Engineering Mechanism: Zero-Copy Memory Streaming & Legal Notarization

Performance and compliance guarantees in Sapmapayı rely upon two foundational architectural patterns:

### Apache Arrow Zero-Copy Streaming
Querying a 250,000-row dataset through conventional REST architectures induces heavy memory and compute friction:
- Database records are deserialized into C# domain objects (millions of short-lived heap allocations causing GC pauses).
- Objects serialize into JSON strings (~25MB payload over the wire).
- The browser parses the text via `JSON.parse()`, blocking the main UI thread for ~800ms.

Sapmapayı replaces this pipeline with Apache Arrow IPC streams. Columnar byte buffers from TimescaleDB map directly into Arrow RecordBatches. Network transfer drops from 24.8MB to 3.1MB (87% bandwidth savings). In the browser, Arrow arrays map directly into `Float64Array` memory buffers without copying, slashing thread latency from 800ms to &lt;15ms.

### Native PDF Rendering and Isolated HSM Queues
Initial prototypes using headless Chromium (Puppeteer) required 400MB+ RAM per instance, leading to out-of-memory container crashes under burst loads. Replacing this with native C# vector rendering (`QuestPDF`) reduced memory footprint to 15MB.

To handle legal enforceability without stalling API throughput, cryptographic operations (X.509 signatures and certified RFC 3161 timestamps) are isolated behind a dedicated PKCS#11 worker queue. Web controllers immediately return job tokens, while background workers batch-sign documents against physical HSM hardware.

## 6. Outcome & Measurable Results
- **Network Payload:** A 250,000-row telemetry dataset dropped from ~24.8MB (JSON) to `~3.1MB` via Apache Arrow IPC (~87% reduction).
- **Browser Thread Unblocking:** UI freezes during JSON parsing (750–900ms) were reduced to `<15ms` using direct typed array buffers.
- **Legal Compliance:** Every generated PDF is cryptographically sealed with national root X.509 digital certificates and RFC 3161 timestamp tokens.
- **Verified Scale:** 500K+ daily processed telemetry records; `<15ms` browser IPC deserialization latency.

## 7. What I Would Do Differently
- Early prototypes used headless Chromium (Puppeteer) for HTML-to-PDF rendering, which consumed 400MB+ RAM per container and failed under concurrent bursts. Rewriting with a native C# layout engine (`QuestPDF`) dropped memory usage to 15MB and slashed render times by 10x.
