## 1. Bağlantı Modeli: Postmaster ve Backend Süreçleri

PostgreSQL sunucusu ayağa kalktığında **`postmaster`** ana süreci çalışır ve gelen bağlantıları dinler. Client'tan yeni bir TCP isteği geldiğinde, `postmaster` işletim sisteminin `fork()` çağrısıyla bağımsız bir **`postgres` backend süreci** türetir.

- **İzolasyon:** Her client oturumu kendi izole bellek alanında koşar. Bir backend çökerse, işletim sistemi seviyesinde temizlenir; diğer oturumlar çalışmaya devam eder.
- **Maliyet:** Her yeni OS süreci Linux üzerinde ~5–10MB temel bellek tüketir. 1000 aktif bağlantı açmak, veritabanına sorgu gelmese dahi 5–10GB RAM'in sırf süreç yönetimine harcanması demektir.
- **Kural:** PostgreSQL doğrudan binlerce doğrudan client bağlantısına açılmamalıdır; önünde mutlaka bağlantı açma/kapama maliyetini sıfırlayan **PgBouncer** gibi hafif bir **Connection Pooler** bulunmalıdır.

## 2. Bellek Mimarisi: Local Memory ve Shared Memory

PostgreSQL'in bellek hiyerarşisi, iki temel felsefe üzerine kuruludur: **Tüm süreçlerin ortaklaştığı Shared Memory** ve **Her client sürecine özel tahsis edilen Local Memory**.

<Mermaid 
  title="2. Bellek Yapısı (Local ve Shared Memory)" 
  ariaLabel="PostgreSQL Local ve Shared Memory Bellek Hiyerarşisi Şeması"
  code={`

    Backend["Backend Process"]

    subgraph LocalMemGroup["Local Memory (Oturuma Özel)"]
        direction LR
        WorkMem["work_mem"]
        MaintMem["maintenance_work_mem"]
        TempBuf["temp_buffers"]
        CatCache["Catalog & Plan Cache"]
    end

    subgraph SharedMemGroup["Shared Memory (Global ve IPC)"]
        direction TB
        subgraph SB["shared_buffers (Data Buffer Pool)"]
            direction LR
            BufHash["Buffer Mapping Hash Table"] --> DescHead["Buffer Descriptors"]
            DescHead --> PoolFrames["Buffer Pool (8KB Data Pages)"]
            ClockSweep["Clock Sweep"] -.->|Eviction İbresi| DescHead
        end
        subgraph OtherShared["Diğer Ortak Alanlar"]
            direction LR
            WALBuf["wal_buffers"]
            ProcArray["Lock & ProcArray"]
        end
    end

    Backend -->|Özel Tahsis| LocalMemGroup
    Backend ==>|IPC ile Ortak| SharedMemGroup

    classDef process fill:#EFF6FF,stroke:#2563EB,stroke-width:1.5px,color:#0F172A

    class WorkMem,MaintMem,TempBuf,CatCache,BufHash,DescHead,PoolFrames,ClockSweep,WALBuf,ProcArray memory
    class SB primary
`}
  summarySteps={[
    "1. Backend Process iki ana bellek kümesine bağlanır: Oturuma Özel Yerel Bellek (Local Memory) ve Ortak Bellek (Shared Memory).",
    "2. Local Memory içinde work_mem (sıralama/hash), maintenance_work_mem (bakım/DDL), temp_buffers (geçici tablolar) ve Catalog/Plan Cache izole çalışır.",
    "3. Shared Memory'nin kalbi olan shared_buffers; Buffer Mapping Hash Table -> Buffer Descriptors -> Buffer Pool (8KB Sayfalar) katmanlarından oluşur.",
    "4. Boş buffer kalmadığında Clock Sweep algoritması Buffer Descriptors dizisini dairesel tarayarak page eviction yapar.",
    "5. wal_buffers ve Lock & ProcArray alanları tüm oturumlar tarafından IPC üzerinden ortaklaşa kullanılır."

/>

- **Local Memory:** Sorgu operatörü başına dinamik ayrılan `work_mem`, bakım işlemlerini üstlenen `maintenance_work_mem`, geçici tablolar için `temp_buffers` ve katalog önbelleklerini (`syscache`/`relcache`) kapsar.
- **Shared Memory:** Tüm backend'lerin ortak buffer pool'u olan `shared_buffers`, WAL kayıtlarını tutan `wal_buffers` ve kilit yöneticisini (`ProcArray`) içerir.

## Mimari Özet

PostgreSQL; process izolasyonu, öngörülebilir bellek havuzları, 8KB data page düzeni ve katı ACID garantileriyle kurulmuş sağlam bir Unix kalesidir. Onu doğru çalıştırmanın anahtarı; bağlantı sayısını kontrol altında tutmak, `shared_buffers` ile OS page cache dengesini kurmak ve `autovacuum` süreçlerini yazma temposuna göre optimize etmektir.
