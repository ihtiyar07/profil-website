Standart `pgvector` eklentisindeki **HNSW** indeksi yüksek arama hızı sunar ancak grafiği tamamen bellekte (`shared_buffers` / RAM) tutmaya dayanır. Vektör sayısı milyonlara çıktığında HNSW indeksi tablo verisinin kendisinden bile daha büyük RAM tüketir; paralel indeks oluşturma sırasında ise yüksek paylaşımlı bellek (`shared memory`) ister.

Timescale'ın Rust ile geliştirdiği açık kaynaklı **[`pgvectorscale`](https://github.com/timescale/pgvectorscale)** eklentisi (`timescaledb-ha:pg16` içinde `0.9.1` sürümüyle hazır gelir), **StreamingDiskANN** algoritması ve **Statistical Binary Quantization (SBQ)** sıkıştırmasıyla vektör indekslerini NVMe/SSD üzerinde verimli şekilde çalıştırır.

## 1. `StreamingDiskANN` ve SBQ Sıkıştırma Akışı

## 2. `HNSW` vs `StreamingDiskANN` Ölçümü (20K × 384-Dim)

`timescale/timescaledb-ha:pg16` (`vector 0.8.7`, `vectorscale 0.9.1`) üzerinde `VECTOR(384)` boyutlu 20.000 satırlık veri kümesinde ölçülen gerçek indeks davranışları:

| Metrik | `pgvector` HNSW | `pgvectorscale` StreamingDiskANN (`memory_optimized`) |
| :--- | :--- | :--- |
| **Tablo Heap Boyutu** | `32 MB` | `32 MB` |
| **İndeks Disk / RAM Ayak İzi** | `39 MB` (Heap'ten büyük) | **`10 MB`** (**~3.9x** daha küçük) |
| **Paralel Build Davranışı** | Varsayılan Docker `/dev/shm` (`64 MB`) içinde `2.14 GB` SHM segmenti isteyerek hata verdi; `max_parallel_maintenance_workers = 0` gerekti | Ek `/dev/shm` ayarı gerektirmeden `24.45 s` içinde hatasız tamamlandı |
| **Top-10 Cosine (`<=>`) Sorgusu** | Maliyet tabanlı planda Planner `DiskANN`'i seçti | `3.96 ms` (Seq Scan + Sort: `8.23 ms`) |

```sql
-- Eklentiyi etkinleştirme (vector bağımlılığını otomatik kurar)
CREATE EXTENSION IF NOT EXISTS vectorscale CASCADE;

-- SBQ sıkıştırmalı DiskANN indeksi
CREATE INDEX idx_vec_diskann
ON vec_events USING diskann (embedding vector_cosine_ops)
WITH (
    storage_layout   = 'memory_optimized',
    num_neighbors    = 50,
    search_list_size = 100
);
```

## 3. Hypertable + `DiskANN` + Label Filtering (`&&`)

RAG, log anomali tespiti veya finansal haber akışlarında yalnızca vektör benzerliği yetmez; **"son 10 günde, kategori=3 olan en benzer 5 olay"** gibi zaman + etiket + vektör birleşik sorguları gerekir. Standart vektör indekslerinde sonradan filtreleme (**post-filtering**) recall kaybına yol açar; `pgvectorscale` ise `SMALLINT[]` etiket sütununu doğrudan `diskann` indeksine gömer:

```sql
CREATE TABLE ts_vec_events (
    created_at TIMESTAMPTZ NOT NULL,
    labels     SMALLINT[]  NOT NULL,
    embedding  VECTOR(384) NOT NULL
);

SELECT create_hypertable('ts_vec_events', 'created_at', chunk_time_interval => INTERVAL '7 days');

-- Vektör + Label birlikte indeksleme (her Chunk için ayrı DiskANN grafiği oluşur)
CREATE INDEX idx_ts_vec_diskann
ON ts_vec_events USING diskann (embedding vector_cosine_ops, labels)
WITH (storage_layout = 'memory_optimized');

-- Zaman budama + indeks içi label filtresi + cosine sıralama
EXPLAIN (ANALYZE, BUFFERS)
SELECT created_at, labels
FROM ts_vec_events
WHERE created_at >= '2026-10-20T00:00:00Z'
  AND labels && ARRAY[3]::SMALLINT[]
ORDER BY embedding <=> $1
LIMIT 5;
```

20.000 satırın 4 haftalık Chunk'a (`5040 + 5040 + 5040 + 4880`) bölündüğü testte bu sorgunun gerçek yürütme planı:
1. İlk 2 Chunk plan aşamasında tamamen dışlandı (**Chunk Exclusion**).
2. Kalan yalnızca 2 Chunk (`_hyper_2_303_chunk` ve `_hyper_2_304_chunk`) üzerinde `Index Scan using ..._diskann` düğümü `Index Cond: (labels && '{3}'::smallint[])` ve `Order By: (embedding <=> $0)` koşullarını aynı anda yürüttü.
3. Sonuçlar `Merge Append` ile birleştirilip toplam **`2.84 ms`** içinde döndürüldü.

> **HA ve Büyük Tablo Notu:** Üretim ortamında çalışan canlı bir Hypertable üzerine sonradan indeks açarken yazma kilitlerini önlemek için `CREATE INDEX CONCURRENTLY` yerine Chunk bazlı indeksleme stratejisi izlenmeli ve streaming replikalardaki WAL yazım artışı (`replication lag`) izlenmelidir.
