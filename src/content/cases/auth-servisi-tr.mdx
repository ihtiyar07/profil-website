## 1. Bağlam
Diverjans bünyesinde geliştirilen Plasmon (IoT telemetri), Sapmapayı (soğuk zincir uyum) ve Diventra WMS (depo yönetim sistemi) platformlarının tümü heterojen mikroservislerden oluşur. Bu sistemlerin tümü, hem kullanıcı oturumlarını hem de saha teknisyeni ve B2B entegrasyon haklarını yöneten tek bir ortak kimlik ve yetki mimarisi üzerinde birleştirildi.

## 2. Problem
Mikroservis dünyasında popüler olan "tamamen durumsuz (stateless) JWT" yaklaşımı sahada kritik bir güvenlik açığı oluşturdu:
- Bir depo operatörünün veya soğutma teknisyeninin yetkileri kaldırıldığında ya da iş akdi feshedildiğinde, elindeki JWT süresi (örn. 60 dakika) bitene kadar yetkili API uç noktalarına istek atmaya devam edebiliyordu.
- JWT içine tüm roller, izinler ve depo/cihaz hiyerarşisi gömüldüğünde HTTP Authorization başlığı 4KB–8KB boyutuna şişiyor, her API isteğinde ağ yükü katlanıyordu.

## 3. Mimari ve Yetki Doğrulama Akışı

Yetkilendirme hattı iki kademeli hibrit doğrulama modeliyle çalışır:

1. **Kompakt İstemci İsteği:** İstemci, API Gateway'e yalnızca sabit kullanıcı kimliğini ve tamsayı oturum sürümünü (`ver`) içeren küçük bir JWT token gönderir (&lt;400 bayt).
2. **Kriptografik İmza Denetimi (JWKS):** API Gateway seviyesinde yerel açık anahtar kullanılarak token süresi ve kriptografik imza asenkron doğrulanır. Bu aşama Redis'e gitmeden geçersiz veya süresi dolmuş token'ları eler.
3. **Bellek İçi Sürüm Doğrulaması (Redis):** İmzası geçerli token'ın sürüm damgası, Redis'teki kullanıcı sürüm anahtarıyla atomik olarak karşılaştırılır (&lt;0.3ms gecikme).
4. **Yönlendirme Kararı:** Sürüm eşleşiyorsa istek downstream mikroservis hattına iletilir (200 OK). Bir yönetici yetkiyi iptal etmiş veya sürümü artırmışsa istek anında kesilir (401 Unauthorized).

## 4. Kararlar ve Elenen Alternatifler

- **Hibrit Model (Stateless JWT Kimliği + Redis Claims) seçildi, saf durumsuz JWT elendi:** Token içinde sadece sabit kimlik bilgileri (`sub`, `iss`, `exp`) taşındı. Değişken yetki ve roller Redis üzerinde kullanıcı anahtarlarında tutuldu. Böylece bir yönetici yetkiyi kaldırdığı anda Redis anahtarı güncellenir ve kullanıcının bir sonraki isteği anında engellenir.
- **Versiyonlanmış Haklar (Versioned Claims) seçildi, Karalama Listesi (Blacklist) elendi:** Milyonlarca iptal edilmiş token hash'ini Redis set'inde aramak (blacklist) bellek ve sorgu maliyetini sürekli büyütür. Bunun yerine kullanıcının tek bir `token_version` tamsayı değeri tutuldu; oturum feshedildiğinde bu tamsayı 1 artırıldı. Eski token'lar anında geçersiz kılındı.
- **Keycloak SSO omurgası korundu:** Kimlik doğrulama, MFA ve federasyon Keycloak üzerinde bırakıldı; yetkilendirme (authorization) ve hızlı oturum iptal motoru ise doğrudan Redis tabanlı özel filtrelerle mikroservis seviyesine indirildi.

## 5. Kritik Sistem Mekanizması: Sürüm Tabanlı O(1) Oturum Feshi

Dağıtık mikroservislerde oturum güvenliği iki temel mimari kararla sağlandı:

### Hibrit Model: Durumsuz Kimlik + Versiyonlanmış Haklar (Versioned Claims)
Tamamen durumsuz JWT'lerde yetki iptali yapılamaz; her istekte veritabanına gitmek ise mikroservis mimarisinin ölçeklenme amacını yok eder.

Geliştirilen hibrit modelde sorumluluklar ayrıştırıldı:
- JWT yalnızca sabit kimlik bilgilerini (`sub`, `iss`, `exp`) ve kullanıcının anlık oturum sürüm numarasını taşır.
- Dinamik yetki setleri ve güncel sürüm damgası Redis kümesinde tutulur.
- Böylece Authorization başlığı 6KB'lık şişkin rol listelerinden &lt;400 baytlık kompakt bir kimlik kartına indirildi (%90+ HTTP başlık tasarrufu).

### O(1) Atomik Sürüm Artırımı ile Anında İptal
Geleneksel oturum iptal yöntemlerinde, iptal edilen her token'ın hash değeri bir kara listede (blacklist) saklanır. Yüz binlerce kullanıcı ve aktif oturumun bulunduğu bir ekosistemde blacklist tutmak bellek tüketimini ve arama maliyetini O(N) karmaşıklıkla sürekli büyütür.

Bu sistemde kara liste tamamen terk edildi:
- Kullanıcı işten çıkarıldığında, şifresini değiştirdiğinde veya rolü güncellendiğinde, Redis'teki oturum sürüm sayacı tek bir atomik komutla artırılır.
- Kullanıcının elinde bulunan ve önceki sürüm numarasını taşıyan tüm aktif token'lar (farklı mobil cihazlar veya tarayıcılar dahil) bir sonraki API isteğinde &lt;1ms içinde geçersiz kalır.
- İşlem maliyeti O(1) sabit zamanda kalır; bellek ayak izi kullanıcı sayısı artsa dahi minimal seviyede korunur.

## 6. Sonuç ve Ölçülebilir Çıktılar
- **Yetki İptal Gecikmesi:** Token süresinin bitmesini (60 dakika) bekleme mecburiyeti kalktı; oturum iptali veya rol değişimi `<1 milisaniye` içinde Plasmon, Sapmapayı ve Diventra WMS genelinde devreye girdi.
- **HTTP Payload Tasarrufu:** JWT token boyutu 5.2KB seviyesinden `<400 bayt` seviyesine indirildi; bu durum özellikle düşük bant genişliğine sahip saha gateway API çağrılarında ciddi tasarruf sağladı.
- **Hafıza ve Performans:** Redis pipeline sorguları downstream mikroservislerde ortalama `0.3ms – 0.5ms` ek gecikmeyle çalıştı.
- **Doğrulanan Ölçek:** 15.000+ eşzamanlı aktif oturum; `<0.4ms` Redis sorgu süresi.

## 7. Neyi Farklı Yapardım?
- Dağıtık Redis kümesinde geçici ağ kopmalarında (network partition) lokal fallback önbellekleme (local in-memory cache with 5s TTL) yapısını daha erken kurmalıydım. Redis ağ kesintisinde sistemin fail-closed davranarak meşru istekleri reddetmesini önlemek için kısa süreli güvenli yerel önbellek mekanizması sonradan eklendi.
