## 1. Sistem Katalogları: `pg_locks` ve `pg_stat_activity`

Kilit analizinde iki temel katalog birlikte değerlendirilir:

- **`pg_locks`:** Çekirdeğin Lock Manager'ı tarafından tutulan tüm kilit girdilerini listeler. `granted = true` kilidin edinildiğini, `granted = false` ise oturumun kuyrukta beklediğini gösterir.
- **`pg_stat_activity`:** Hangi `pid`'in hangi sorguyu çalıştırdığını, transaksiyon başlangıç zamanını (`xact_start`) ve oturum durumunu (`active`, `idle in transaction`) sunar.

## 2. Production Blocking Analiz Sorgusu

PostgreSQL 9.6 ile gelen `pg_blocking_pids()` fonksiyonu sayesinde karmaşık `self-join` sorgularına gerek kalmadan bloklayan ve bekleyen tüm oturumlar tek bir sorguyla filtrelenebilir:

```sql
SELECT
    blocked.pid AS blocked_pid,
    blocked.usename AS blocked_user,
    now() - blocked.query_start AS waiting_duration,
    blocked.wait_event_type,
    blocked.wait_event,
    blocking.pid AS blocking_pid,
    blocking.usename AS blocking_user,
    blocking.state AS blocking_state,
    now() - blocking.xact_start AS blocking_xact_age,
    left(blocking.query, 60) AS blocking_query,
    left(blocked.query, 60) AS blocked_query
FROM pg_stat_activity blocked
JOIN unnest(pg_blocking_pids(blocked.pid)) AS blocker_pid ON true
JOIN pg_stat_activity blocking ON blocking.pid = blocker_pid
ORDER BY waiting_duration DESC;
```

## 3. Müdahale: `pg_cancel_backend` vs `pg_terminate_backend`

Sistemi tıkayan bir oturum tespit edildiğinde iki farklı sonlandırma aracı kullanılır:

- **`pg_cancel_backend(pid)`:** Oturumun o an çalıştırdığı sorguya `SIGINT` sinyali göndererek yalnızca sorguyu iptal eder. Oturum bağlantısı açık kalır. Eğer sorun `idle in transaction` ise bu komut işe yaramaz.
- **`pg_terminate_backend(pid)`:** Oturuma `SIGTERM` sinyali göndererek bağlantıyı tamamen koparır ve açık transaksiyonu `ROLLBACK` ettirir. Tıkanıklıkları çözmede en kesin yöntemdir.

## 4. Laboratuvar: Blocking Zinciri Oluşturma ve Teşhis

Aşağıdaki adımlarla kontrollü bir kilit darboğazı oluşturup analiz sorgumuzla yakalayalım.

### Adım 1: Test Ortamını Hazırlama
```sql
CREATE TABLE orders (id int PRIMARY KEY, total numeric, status text);
INSERT INTO orders VALUES (1, 150.0, 'pending');
```

### Adım 2: Kilit Oluşturma ve Bekleme
```sql
-- Terminal 1 (Bloklayan Oturum):
BEGIN;
UPDATE orders SET total = 200.0 WHERE id = 1;
-- Bilerek COMMIT yapmıyoruz, transaksiyon açık kalıyor!

-- Terminal 2 (Bekleyen Oturum):
UPDATE orders SET total = 300.0 WHERE id = 1;
-- Terminal 2 kilit nedeniyle askıda kalır (Lock beklemesi).
```

### Adım 3: Terminal 3'te Analiz ve Müdahale
Üçüncü bir terminal açarak teşhis sorgumuzu çalıştıralım:

```sql
-- Hangi PID kimi blokluyor?
SELECT blocked.pid AS blocked_pid,
       blocking.pid AS blocking_pid,
       blocking.state AS blocker_state,
       blocked.wait_event
FROM pg_stat_activity blocked
JOIN unnest(pg_blocking_pids(blocked.pid)) AS blocker_pid ON true
JOIN pg_stat_activity blocking ON blocking.pid = blocker_pid;
```

Örnek çıktı:
```text
 blocked_pid | blocking_pid |    blocker_state    | wait_event 
-------------+--------------+---------------------+------------
       41205 |        41189 | idle in transaction | tuple
```

Görüldüğü gibi `blocking_pid = 41189`, transaksiyonu açık bırakıp unuttuğu için (`idle in transaction`) diğer oturumu `tuple` kilidinde bekletmektedir.

```sql
-- Düğümü çözmek için bloklayan oturumu sonlandıralım:
SELECT pg_terminate_backend(41189);
```

Komut çalıştırıldığı anda Terminal 1 oturumu düşürülür, Terminal 2'deki `UPDATE` anında başarıyla tamamlanır.
