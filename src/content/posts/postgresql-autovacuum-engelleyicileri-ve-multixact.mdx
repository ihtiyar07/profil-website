Autovacuum arka planda sürekli çalışıyor görünmesine rağmen tablolardaki `n_dead_tup` sayısı düşmüyor ve disk dolmaya devam ediyorsa, sistemde **Oldest Active Snapshot xmin** değerinin ilerlemesini engelleyen bir bloklayıcı vardır.

---

## 1. Dead Tuple Temizliğini Engelleyen Dört Büyük Faktör

Autovacuum bir ölü satırı ancak ve ancak **sistemdeki hiçbir aktif transaksiyonun o satırı görme ihtimali kalmadığında** temizleyebilir. Bunu engelleyen başlıca kaynaklar şunlardır:

1. **Uzun Süren Sorgular:** Saatlerce süren bir analitik sorgu başladığı andaki `xmin` değerini tutar; bu süreç bitene kadar ondan sonra üretilen hiçbir dead tuple silinemez.
2. **`idle in transaction` Oturumlar:** Bir uygulamanın `BEGIN` deyip unuttuğu atıl oturumlar tüm veritabanının temizliğini durdurur.
3. **Geride Kalan Replikasyon Slotları (`pg_replication_slots`):** Mantıksal veya fiziksel replikasyon abonesi koptuğunda veya geride kaldığında, slot `catalog_xmin` veya `xmin` değerini dondurur ve WAL ile dead tuple temizliğini felç eder.
4. **Hazırlanmış Transaksiyonlar (Orphan Prepared Transactions):** İki fazlı commit (2PC) mimarisinde `PREPARE TRANSACTION` ile askıda bırakılan işlemler `ROLLBACK PREPARED` edilene kadar horizon'u kilitler.

## 2. Multixact ve `track_commit_timestamp`

### Multixact Mimarisi (`pg_multixact`)
Bir satırın başlığında tek bir `t_xmax` alanı bulunur. Eğer birden fazla transaksiyon aynı anda aynı satır üzerinde paylaşımlı kilit alırsa (`FOR SHARE` veya `FOR KEY SHARE`), PostgreSQL tekil bir XID yazamaz. Bunun yerine bir **MultiXactId** üretir ve bu kimliğe dahil olan transaksiyonları `$PGDATA/pg_multixact` dizininde eşler.

### `track_commit_timestamp` ile Adli Bilişim (Forensics)
`postgresql.conf` içinde `track_commit_timestamp = on` açıldığında çekirdek her transaksiyonun kesin onaylanma saatini kaydeder. Böylece bir satırın ne zaman veritabanına girdiği sorgulanabilir:

```sql
SELECT id, name,
       pg_xact_commit_timestamp(xmin) AS olusturulma_zamani
FROM customers;
```

## 3. Laboratuvar: Autovacuum'un Engellenmesini Kanıtlama

### Adım 1: Test Tablosu Hazırlama
```sql
CREATE TABLE vacuum_block_test (id int, val text);
INSERT INTO vacuum_block_test VALUES (1, 'ilk_hali');
```

### Adım 2: Terminal 1'de Transaksiyonu Açık Tutma
```sql
-- Terminal 1:
BEGIN;
SELECT * FROM vacuum_block_test;
-- Transaksiyon açık kalır, COMMIT yapılmaz!
```

### Adım 3: Terminal 2'de Güncelleme ve Temizlik Denemesi
```sql
-- Terminal 2:
UPDATE vacuum_block_test SET val = 'ikinci_hali';
UPDATE vacuum_block_test SET val = 'ucuncu_hali';

-- Manuel VACUUM çalıştıralım:
VACUUM VERBOSE vacuum_block_test;
```

Konsol çıktısında:
```text
INFO:  "vacuum_block_test": found 2 removable, 2 nonremovable row versions in 1 out of 1 pages
DETAIL:  2 dead row versions cannot be removed yet, because they are still required for other transactions.
```
Görüldüğü gibi 2 adet dead tuple **Terminal 1 açık olduğu için silinemedi!**

### Adım 4: Engelleyiciyi Kapatıp Temizliği Tamamlama
```sql
-- Terminal 1'de:
COMMIT;

-- Terminal 2'de tekrar çalıştıralım:
VACUUM VERBOSE vacuum_block_test;
-- INFO: 2 dead row versions removed. Artık tamamen temizlendi!
```
