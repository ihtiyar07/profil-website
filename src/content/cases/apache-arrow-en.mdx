## 1. Context
In large-scale telemetry and analytical applications, users frequently request high-resolution time-series queries spanning 30-day horizons, financial order books, or industrial asset telemetry for real-time visualization.

Executing such queries requires moving hundreds of thousands of datapoints (timestamps, floating-point metrics, bitmask status codes) to client browsers. This project eliminated serialization and deserialization bottlenecks between database engines and browser visualization layers.

## 2. The Problem: JSON Bottlenecks and UI Thread Starvation

Conventional web architectures serialize SQL result sets into JSON strings at the API layer. For a 250,000-row payload:
1. **Server CPU and GC Pressure:** Instantiating hundreds of thousands of intermediate heap objects in C# or Node.js triggers heavy garbage collection pauses and burns CPU cycles on string formatting.
2. **25MB Bloated Payload:** JSON's repetitive key-value syntax (`{"timestamp": 1714521000, "temperature": 4.12}`) bloats the network payload to ~24.8MB.
3. **Browser Thread Stalls:** Executing `JSON.parse()` on the client locks the single-threaded JavaScript engine for over 850 milliseconds, dropping frames and causing unresponsive UI freezes.

## 3. Architecture: Zero-Copy Columnar IPC Streaming

The system replaced text serialization with binary **Apache Arrow IPC Streaming**:

```
Database Engine (TimescaleDB)
    ↓ ADO.NET / Npgsql DataReader
Backend Pipeline (Arrow RecordBatch Builder)
    ↓ HTTP/2 Stream (application/vnd.apache.arrow.stream)
Browser Memory (ArrayBuffer)
    ↓ Zero-Copy Memory View
Float64Array / WebGL Canvas (<15ms Render)
```

### A. Direct Columnar RecordBatch Building
Instead of instantiating row-level DTOs, the backend streaming engine packs database reader buffers directly into contiguous columnar memory arrays (Timestamp arrays, Float64 arrays).

### B. HTTP/2 IPC Streaming
Constructed Apache Arrow `RecordBatch` frames stream across HTTP/2 with the `application/vnd.apache.arrow.stream` media type. The browser receives and parses the first batch before the query finishes executing on the server.

### C. Zero-Copy Client Memory Views
The binary payload lands in the browser as a raw `ArrayBuffer`. The Apache Arrow JavaScript SDK points typed array views directly to the underlying memory address:
- No string parsing, no memory re-allocations, zero object copies.
- 250,000 double-precision values pass directly to WebGL rendering buffers in &lt;15ms at a sustained 60 FPS.
