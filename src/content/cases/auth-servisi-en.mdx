## 1. Context
Across Diverjans products—Plasmon (IoT telemetry), Sapmapayı (compliance), and Diventra WMS (warehouse operations)—microservices run on heterogeneous stacks (.NET 10 and Spring Boot 3). A single unified identity and authorization plane was required to govern warehouse personnel, field technicians, and B2B integrations.

## 2. Problem
Standard stateless JWT architectures present an unacceptable security vulnerability in enterprise operations:
- When an operator is terminated or an edge device compromised, the existing signed JWT remains fully valid until its expiration (e.g., 60 minutes), allowing unauthorized access to critical machinery endpoints.
- Embedding deep granular role trees into the JWT inflated HTTP Authorization headers to 4KB–8KB, multiplying bandwidth costs across millions of sensor requests.

## 3. Architecture & Verification Flow

The authorization pipeline operates via a two-stage hybrid verification model:

1. **Compact Client Token:** Clients supply the API Gateway with a minimal JWT (&lt;400 bytes) containing immutable user identity and an incrementing session integer (`ver`).
2. **Cryptographic Signature Verification (JWKS):** The API Gateway verifies token expiration and asymmetric cryptographic signature against public keys, eliminating malformed or expired requests without hitting Redis.
3. **In-Memory Version Assertion (Redis):** Valid tokens trigger an atomic comparison of the token's version integer against the current active version key in Redis (&lt;0.3ms latency).
4. **Routing Outcome:** If versions match, the request passes through to downstream microservices (200 OK). If access was revoked or version bumped, the session immediately terminates (401 Unauthorized).

## 4. Decisions & Rejected Alternatives

- **Hybrid Model (Stateless JWT ID + Redis Claims) chosen, pure stateless JWT rejected:** The JWT holds only immutable identity claims (`sub`, `iss`, `exp`). Volatile roles (`permissions: ["telemetry:write", "chiller:override"]`) reside in Redis. Revoking access takes a single atomic key update, cutting off subsequent requests in `<1ms`.
- **Versioned Claims chosen, Token Blacklists rejected:** Querying an ever-growing Redis set of revoked token IDs incurs ballooning memory overhead. Instead, each identity maintains an incrementing integer `token_version`; bumping the version instantly invalidates all previously issued tokens.
- **Keycloak retained for SSO core:** Federation, MFA, and OAuth2 identity management remain with Keycloak, while high-frequency authorization and instant revocation are delegated to localized Redis filter layers.

## 5. Core Engineering Mechanism: Versioned O(1) Session Invalidation

Distributed authorization security is grounded in two architectural principles:

### Hybrid Identity: Stateless Claims + Versioned Revocation
Pure stateless JWTs prevent instant revocation, while querying a central database on every HTTP call defeats microservice scalability.

The hybrid architecture establishes clear separation of concerns:
- JWTs carry only immutable identity fields (`sub`, `iss`, `exp`) alongside the user's active session version (`ver: 3`).
- Granular permissions and active version counters reside inside the Redis cache cluster.
- This design slashes HTTP Authorization headers from 6KB role trees to compact &lt;400-byte tokens, saving over 90% in header overhead across IoT calls.

### Instant Revocation via Atomic O(1) Version Bumps
Conventional session termination strategies maintain blacklists of revoked token IDs. Across hundreds of thousands of users and volatile IoT sessions, blacklists cause unbounded memory expansion and O(N) lookup degradation.

Blacklists were discarded entirely:
- When an operator is suspended, credentials changed, or permissions altered, the `auth:ver:{userId}` key in Redis increments atomically (`INCR`).
- Any active tokens carrying outdated version numbers (`ver: 3`) across mobile devices or terminals are rejected on their next API request in &lt;1ms.
- Lookup complexity remains strictly O(1), maintaining deterministic memory usage regardless of transaction volume.

## 6. Outcome & Measurable Results
- **Revocation Delay:** Dropped from 60 minutes to `<1 millisecond` across all microservices.
- **Header Payload:** JWT footprint decreased from 5.2KB down to `<400 bytes`, critical for low-bandwidth cellular field gateways.
- **Overhead:** Added Redis check adds only `0.3ms – 0.5ms` per request.
- **Verified Scale:** 15,000+ concurrent active sessions; `<0.4ms` Redis lookup latency.

## 7. What I Would Do Differently
- An in-memory local fallback cache (5s TTL) should have been included earlier to handle transient Redis cluster partitions gracefully, avoiding fail-closed rejection of legitimate requests during momentary network blips.
